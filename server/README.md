# Сервер данных TAnalytic

Небольшой HTTP-сервер (один файл `tinvest_server.py`, только стандартная библиотека Python 3.8+), который стоит между
приложением и публичными источниками данных и **кэширует** их ответы для всех пользователей.

## Зачем и как это устроено

```
приложение  ──►  сервер данных  ──►  MOEX ISS, ФНС ГИР БО, Банк России, smart-lab, рейтинговые агентства
(на компьютере)   (кэш + лимиты)      (публичные страницы и API)
```

Без сервера каждый пользователь сам делает сотни запросов к Мосбирже и ФНС. С сервером запрос идёт один раз, ответ
сохраняется в общем кэше и отдаётся всем, а нагрузка на источник ограничивается (Мосбиржа ~8 запросов/с, ФНС 2/с, smart-lab 1/с, остальные 2/с).

Что делает сервер:

- `GET /v1/health` — открыт без ключа: `{ok, version, uptime, cache_items, auth: "keys"|"key"|"none", bot}`;
- `GET /v1/auth/check` — проверка ключа из `X-Client-Key`: 200 `{ok, expires, username, plan: "pro"|"free", pro_until, trial: true|false, bot}` или 401 `{ok:false, error:"invalid"|"expired"|"banned", bot}`;
- `POST /v1/notify` — поставить в очередь Telegram-уведомление пользователю (см. «Уведомления через бота» ниже);
- `GET /v1/stats` — счётчики по хостам, доля попаданий в кэш, ошибки источников (без адресов клиентов);
- `GET|POST /v1/fetch?url=<url-кодированный адрес>` — получить страницу источника. Ответ: статус источника, тело (в том числе
  бинарное, например PDF Банка России), `Content-Type`, заголовки `X-Cache: hit|miss|stale` и `X-Age`.
- `GET /v1/parsed/<имя>?...` — готовый разбор страницы источника (тот же ключ, тот же кэш и лимиты, что у `/v1/fetch`; страница берётся с TTL своего хоста).
  Ответ: `{"ok":true,"v":1,"data":…}` либо `{"ok":false,"error":"…"}` (`unknown parser` — 404, `bad ticker` — 400, `upstream failed` — 502,
  `upstream status N` / `parse failed` — 200). Разбор выполняется функциями в `tinvest_server.py`: когда сайт меняет разметку, достаточно задеплоить сервер.
  Клиент при любом `ok:false`, 404 (старый сервер) или несовпадении `v` разбирает страницу сам. Эндпоинты:
  - `/v1/parsed/investmint/placements` — календарь первичных размещений investmint.ru: `data` — список строк `{issuer, short, desc, isin, start, end, book, status, link}`;
  - `/v1/parsed/smartlab/ifrs?ticker=SBER` — таблица МСФО smart-lab.ru: `data` = `{labels: ["2021", …, "LTM"], rows: {поле: [значения по меткам]}}`.
  Парсеры дублируют клиентские (`src/py/13_ext_market.py`, `src/py/13m_ifrs.py`); их надо менять синхронно, `tests/test_parsed.py` сверяет результаты.

Правила:

- Разрешены только публичные хосты из списка в коде (`ALLOWED_HOSTS`): `iss.moex.com`, `www.moex.com`, `bo.nalog.gov.ru`, `www.cbr.ru`, `cbr.ru`,
  `smart-lab.ru`, `raexpert.ru`, `ratings.ru`, `investmint.ru`, `invest-brands.cdn-tinkoff.ru`, `t.me/s/…` (зеркало канала с рейтингами).
  Всё остальное получает 403, как и редиректы на посторонние хосты. API Т-Инвестиций и Telegram Bot API в списке нет (уведомления идут не через `/v1/fetch`, а через `/v1/notify` и бота).
- Время жизни кэша задаётся таблицей `RULES` в коде: котировки и списки Мосбиржи — 5 минут в торговые часы (иначе час), история и описания — 1–3 суток,
  эмитенты — 7 суток, кривая КБД — час, ФНС — 7 суток, smart-lab — 5 суток, Банк России — 6–12 часов, рейтинги — 12 часов, логотипы — 30 суток, прочее — час.
- Если источник недоступен, отдаётся устаревшая копия (`X-Cache: stale`). Ответы 5xx не кэшируются, 404 кэшируется на 10 минут.
- Одинаковые одновременные запросы объединяются в один запрос к источнику.
- POST кэшируется только по явному правилу (сейчас — поиск эмитента на raexpert.ru); ключ кэша — адрес и хэш тела.
- Размер кэша ограничен (`--max-mb`, по умолчанию 1024); при переполнении удаляются записи, к которым дольше всего не обращались.

Клиент при любой проблеме сервера (нет связи, таймаут, 5xx, неверный ключ) молча ходит к источникам напрямую и на 5 минут перестаёт обращаться к серверу.

## Что видит сервер, что хранит

- **Видит:** адреса публичных страниц, которые запрашивает приложение. В них бывают ISIN, тикеры и ИНН бумаг и эмитентов, которые
  пользователь открывает. IP-адреса клиентов в статистике не хранятся.
- **Не видит:** токен Т-Инвестиций, счета, позиции, операции. Они идут напрямую в Т-Банк и на сервер не попадают.
  Исключение — тексты уведомлений, которые пользователь сам включил в приложении (названия бумаг и суммы в тревогах и сводке): они проходят через сервер и бот.
- **Хранит:** кэш публичных ответов в SQLite: `cache.sqlite` (режим WAL) в каталоге `--data`. Текст уведомлений лежит в очереди `outbox` общей базы бота только до отправки
  и удаляется сразу после доставки; в журнал текст не пишется. Для лимитов хранятся лишь пары «Telegram ID, время» (`notify_log`, записи старше суток удаляются).
- **Журнал:** по умолчанию адреса запросов не пишутся. Флаг `--verbose` включает строки вида `GET /v1/fetch?url=…` (для отладки).
- Если запускаете сервер для других людей, скажите им, что запрошенные адреса источников проходят через ваш сервер.

## Запуск локально

```
python3 server/tinvest_server.py                       # 127.0.0.1:8780, кэш в ~/.tinvest_server
python3 server/tinvest_server.py --port 8780 --data ./srvdata --key МОЙ_КЛЮЧ
python3 server/tinvest_server.py --version
```

Флаги: `--host`, `--port`, `--data`, `--key` (или переменная `TINVEST_SERVER_KEY`), `--keys-db` (`TINVEST_KEYS_DB`), `--bot` (`TINVEST_BOT`), `--max-mb`, `--verbose`.
Если задан ключ, каждый запрос обязан содержать заголовок `X-Client-Key` (сравнение за постоянное время); без ключа сервер открыт для всех, кто до него дотянется,
поэтому на публичном адресе ключ нужен.

Подключение приложения: «Настройки → Сервер данных» (адрес, например `http://127.0.0.1:8780`, и ключ, кнопка «Проверить») либо
переменные окружения `TINVEST_DATA_SERVER` и `TINVEST_DATA_KEY` перед запуском приложения.

## Развёртывание на VPS

Сервер данных и Telegram-бот работают на одном VPS от одного пользователя `tinvest` и делят базу ключей
`/var/lib/tinvest-bot/keys.sqlite`. Код ставится git-клонами, каждую ночь в 03:00 МСК таймер подтягивает обновления
и перезапускает только то, что изменилось. Готовые файлы лежат в `server/deploy/`.

1. Пользователь и каталоги:

   ```
   sudo useradd --system --home /var/lib/tinvest-server --shell /usr/sbin/nologin tinvest
   sudo mkdir -p /var/lib/tinvest-server /var/lib/tinvest-bot
   sudo chown tinvest:tinvest /var/lib/tinvest-server /var/lib/tinvest-bot
   ```

2. Код сервера (публичный репозиторий):

   ```
   sudo git clone https://github.com/Kos5o4ka/tinvest-analytics.git /opt/tinvest-analytics
   ```

3. Код бота (закрытый репозиторий) через deploy-ключ только на чтение:

   ```
   sudo ssh-keygen -t ed25519 -N "" -f /root/.ssh/tinvest_bot_deploy
   sudo cat /root/.ssh/tinvest_bot_deploy.pub
   ```

   Добавьте ключ в GitHub: репозиторий tinvest-bot → Settings → Deploy keys → Add deploy key (галочку «Allow write access» не ставьте). Затем:

   ```
   sudo GIT_SSH_COMMAND="ssh -i /root/.ssh/tinvest_bot_deploy -o IdentitiesOnly=yes" \
        git clone git@github.com:Kos5o4ka/tinvest-bot.git /opt/tinvest-bot
   sudo git -C /opt/tinvest-bot config core.sshCommand "ssh -i /root/.ssh/tinvest_bot_deploy -o IdentitiesOnly=yes"
   ```

4. Настройки бота: `sudo cp /opt/tinvest-bot/.env.example /etc/tinvest-bot.env && sudo chmod 600 /etc/tinvest-bot.env`, впишите `BOT_TOKEN`
   от @BotFather и свой Telegram ID в `ADMIN_ID`, `KEYS_DB=/var/lib/tinvest-bot/keys.sqlite`.
   По желанию общий ключ для своих клиентов и мониторинга: `echo 'TINVEST_SERVER_KEY=длинная_случайная_строка' | sudo tee /etc/tinvest-server.env`.

5. Сервисы и таймер:

   ```
   sudo cp /opt/tinvest-bot/tinvest-bot.service /etc/systemd/system/
   sudo cp /opt/tinvest-analytics/server/deploy/tinvest-server.service \
           /opt/tinvest-analytics/server/deploy/tinvest-update.service \
           /opt/tinvest-analytics/server/deploy/tinvest-update.timer /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now tinvest-bot          # первым: создаёт базу ключей
   sudo systemctl enable --now tinvest-server
   sudo systemctl enable --now tinvest-update.timer
   ```

6. Проверка:

   ```
   curl http://127.0.0.1:8780/v1/health                 # "auth": "keys", "bot": "tanalyticbot"
   systemctl list-timers tinvest-update.timer           # когда следующий запуск
   journalctl -u tinvest-bot -u tinvest-server -n 50    # журналы
   ```

   Напишите боту `/start`, получите ключ и проверьте: `curl -H "X-Client-Key: TIA-…" http://127.0.0.1:8780/v1/auth/check`.

Если сервер уже работал по старой схеме (`/opt/tinvest-server/tinvest_server.py`), остановите и отключите старый юнит перед шагом 5,
кэш в `/var/lib/tinvest-server` подхватится новым сервисом.

## Сборщик сообщений о раскрытии (`disclosure_worker.py`)

Отдельный процесс (тоже только stdlib), который собирает сообщения эмитентов по облигациям (выплаченные и начисленные доходы, неисполнение
обязательств, итоги приобретения, досрочное погашение) и раскладывает их в факты по ISIN. Сервер данных отдаёт их клиентам из готовой базы.

- **Откуда:** `e-disclosure.azipi.ru` (открытое зеркало; лента сообщений по дням `/messages/list/day-ДД.ММ.ГГГГ/…` и страницы сообщений `/messages/<id>/`).
  `e-disclosure.ru` не используется. Универсум эмитентов — ИНН облигаций, торгуемых на MOEX (ISS `securities.json`, обновляется раз в сутки).
- **Как часто:** один поток, не чаще 1 запроса в 1,5 с к azipi (`--pace`), к ISS — 0,3 с. Честный `User-Agent: TAnalytic-disclosure/1.0 (+репозиторий)`.
  При 429/5xx/сетевых ошибках — повтор с растущей паузой (уважает `Retry-After`), после 5 ошибок подряд — пауза 10 минут.
- **Режимы:** *live* — каждые `--interval` (60 с) читает ленту сегодняшнего дня с первой страницы, пока не встретит страницу с уже известными id; после полуночи по Москве
  один раз дособирает вчерашний день; качает тексты нужных сообщений (`wanted`: ИНН из универсума и подходящий заголовок, список `WANTED_TITLES` в коде).
  *backfill* — история от вчера назад по дням до `--since` (по умолчанию 2015-01-01) или до 60 календарных дней подряд без сообщений (конец архива запоминается).
  Live-цикл имеет приоритет: между днями истории проверяется, не пора ли его запустить.
- **База:** `<--data>/disclosure.sqlite` (WAL): `universe`, `feed` (все элементы ленты — метаданные), `docs` (тексты), `facts` (разобранные факты, `parser_ver`), `days` (прогресс истории), `meta`.
  Разбор текста делают те же `doc_text`/`dc_extract`, что в клиенте: воркер подгружает собранный `tinvest_analytics.py` из корня репозитория (`--lib`), поэтому в репозитории он должен быть собран (`python3 build.py`).
- **Сколько собирается история:** будний день ≈ 64 страницы ленты (10 сообщений на странице; 470–640 сообщений) + 30–60 текстов нужных сообщений: около 100–160 запросов,
  то есть ≈ 2,5–4 минуты при `--pace 1.5`. Выходные пустые (1 запрос). С 2015 года ~3100 будних дней, более ранние годы заметно короче: порядка 5–7 суток непрерывной работы. Live при этом не страдает.
  Оценка по фактическим данным: `--stats` (поле `eta_days`).
- **Чтение клиентами** (тот же ключ, что у остальных `/v1/parsed/…`, ответ не кэшируется, нет базы — пустой результат):
  - `/v1/parsed/disclosure/facts?isin=RU000A10B024` или `?inn=7703104630` (+ `kind=coupon_paid|coupon_declared|default|buyback_result|other`, `limit`, по умолчанию 200) — факты, новые первыми:
    `{doc_id, title, published, url, isin, inn, kind, event_date, due_date, conf, data}`;
  - `/v1/parsed/disclosure/defaults?since=ГГГГ-ММ-ДД` (по умолчанию 30 дней назад) — факты о неисполнении обязательств;
  - `/v1/parsed/disclosure/status` — счётчики и диапазон истории (то же, что `--stats`).

Запуск и установка:

```
python3 server/disclosure_worker.py --data DIR                 # постоянный режим (live + история), напрямую к azipi
python3 server/disclosure_worker.py --data DIR --crowd         # то же, но страницы приходят от приложений пользователей (см. ниже; так работает unit)
python3 server/disclosure_worker.py --data DIR --once --days 2 # один live-цикл + 2 дня истории и выход (для проверки/cron)
python3 server/disclosure_worker.py --data DIR --stats         # счётчики, диапазон истории, оценка времени до конца
python3 server/disclosure_worker.py --data DIR --reparse       # заново разобрать сохранённые тексты после обновления парсера
sudo cp /opt/tinvest-analytics/server/deploy/tinvest-disclosure.service /etc/systemd/system/     # запускается с --crowd
sudo systemctl daemon-reload && sudo systemctl enable --now tinvest-disclosure
journalctl -u tinvest-disclosure -f                            # строки «день …: страниц, элементов, новых, нужных», «тексты: загружено»
```

Остальные флаги: `--crowd`, `--pace`, `--interval`, `--since ГГГГ-ММ-ДД`, `--no-backfill` (только live), `--lib PATH`, `--verbose`. SIGTERM останавливает процесс корректно.
Юнит работает от `tinvest` и пишет только в `/var/lib/tinvest-server`; ночное обновление `tinvest-update.sh` перезапускает его вместе с сервером данных, если он включён.
После обновления парсера (`src/py/12c_disclosure_parse.py`, пересобранный `tinvest_analytics.py`) выполните `--reparse` (остановите сервис на время или запускайте от того же пользователя: SQLite WAL терпит параллельное чтение, но запись одна).

## Сбор раскрытий силами пользователей (режим `--crowd`)

`e-disclosure.azipi.ru` блокирует адрес VPS (TCP соединяется, TLS не завершается), а у пользователей из России сайт открывается. Поэтому на сервере
сборщик запускается как `disclosure_worker.py --data DIR --crowd` (так теперь настроен `tinvest-disclosure.service`): сам он к azipi **не ходит**.
Логика сборщика прежняя (универсум по ISS, лента дня, тексты, разбор, `facts`), но каждый нужный адрес azipi не скачивается, а становится заданием в очереди
`<--data>/crowd.sqlite` (WAL, общая для процесса сервера данных и процесса сборщика), а страницы берутся из принятых пользовательских присылок. ISS Мосбиржи качается напрямую.
Без `--crowd` сборщик работает как раньше (напрямую; нужен доступ к azipi, например через прокси) — оба режима независимы.

Как идёт работа:

- Сборщик, узнав, что ему нужно, ставит в очередь сразу всё: все страницы `PAGEN_2=N` дня, как только первая страница показала их число; тексты всех нужных сообщений; первые страницы
  ближайших трёх дней истории. Несколько приложений берут задания параллельно, а день разбирается, когда пришли все его страницы (до этого ничего не записывается и день не помечается «partial»).
- Приоритеты (меньше — раньше): 0 живая лента сегодня (считается свежей `LIVE_AGE` = 10 минут, потом просится заново), 1 вчера, 2 тексты сообщений, 3 история от новых дней к старым, 4 заглядывание вперёд.
  Страница ленты дня, присланная до конца этого дня, для вчера и истории неполна и не годится.
- Задания выдаются в аренду на 5 минут (`LEASE_SEC`); не вернули — выдаются другому. Повторный запрос того же ключа возвращает те же ещё не сданные задания. Неудача (отказ проверки, 5xx у клиента) возвращает задание с паузой;
  8 неудач — задание `failed`, сборщик видит его как постоянный отказ (`Gone`). 404 принимается как «сообщения нет», когда это подтвердили два разных ключа (или один — после трёх попыток).
- Нет ни одного участника — очередь просто копится: данные не пропадают, новые факты не появляются, прежние отдаются как раньше; сборщик при этом ничего не теряет и не ошибается.

Эндпоинты (тот же заголовок `X-Client-Key`, что у остальных `/v1/*`; **анонимный доступ отклоняется всегда**, даже если сервер запущен без ключей — 401):

- `GET /v1/crowd/task?n=2` (n от 1 до 5) → `{ok, tasks: [{id, url}], queue, retry_after}`; `retry_after` = 300, если заданий нет. Выдаются только адреса двух форм на `https://e-disclosure.azipi.ru`:
  `/messages/list/day-ДД.ММ.ГГГГ/?MESSAGE_BY_DAY=ДД.ММ.ГГГГ&PAGEN_2=N` и `/messages/<id>/`.
- `POST /v1/crowd/submit` с JSON `{id, url, status, body_b64, ctype}` (`body_b64` — gzip+base64 исходных байтов страницы; для 404/410 пустой). Проверки: задание существует и адрес совпадает; размер после
  распаковки не больше 2 МБ (413); страница похожа на ожидаемую (лента содержит запрошенную дату, сообщение — свой номер и метку azipi; captcha и страницы ошибок отклоняются, 422);
  не чаще одной отправки в 5 секунд на ключ и 6000 в сутки (429 с `retry_after`). Ответ `{ok, accepted, ...}`.
- `GET /v1/crowd/status` → `{queue, leased, failed, accepted_today, contributors_24h, oldest_queued_age}` — только агрегаты, идентификаторы ключей не отдаются.

Приём страниц. Первая прошедшая проверку страница принимается сразу (пользователей может быть очень мало) и запоминается с ключом отправителя и sha256 нормализованного тела
(без скриптов, комментариев, скрытых полей сессии и разницы в пробелах). Принятые страницы (сообщения) иногда (~4% выдач, когда очередь пуста — всегда) отдаются на перепроверку другому ключу. Если другой
ключ присылает иное содержимое по тому же адресу, при равенстве остаётся принятое и просится третье мнение; когда набирается большинство разных доверенных ключей за другой вариант, страница заменяется,
сборщик получает событие и заново загружает и разбирает это сообщение (для страниц ленты только журнал: уже добавленные элементы остаются). Расхождения пишутся в журнал сервера. Принятые страницы и задания хранятся 7 суток.

Недоверие к ключу: `python3 server/crowd.py --data /var/lib/tinvest-server distrust tg:123456` — присылки ключа игнорируются (ответ для него не меняется), задания ему не выдаются, принятые им страницы
возвращаются в очередь (или заменяются сохранённым вариантом другого доверенного ключа), сборщик перезагружает затронутые сообщения. `trust ID` отменяет, `keys` показывает счётчики по ключам, `status` — очередь. Идентификатор — `tg:<Telegram ID>`
для ключей бота и `key` для общего `--key`.

Клиент (приложение, `src/py/13o_crowd.py`): настройка «Помогать собирать раскрытия эмитентов» в «Настройках» выключена по умолчанию. Если включена, пока программа запущена и подключён сервер данных, фоновый поток берёт задания,
скачивает страницы azipi **напрямую** (не через `/v1/fetch`), не чаще раза в 15 секунд, после ошибок azipi (сеть, 403/429/5xx, captcha) молчит 30 минут, при отсутствии заданий или недоступном сервере опрашивает снова через 5–10 минут.
Адрес задания проверяется и в приложении (только две формы страниц azipi). На сервер уходят только адрес, статус и страница, ничего личного.

## Cloudflare Tunnel

Сервер слушает только `127.0.0.1`, наружу его выставляет именованный туннель `cloudflared`: открывать порты на VPS не нужно.

```
cloudflared tunnel login
cloudflared tunnel create tinvest-data
cloudflared tunnel route dns tinvest-data data.example.ru
```

`/etc/cloudflared/config.yml`:

```
tunnel: tinvest-data
credentials-file: /etc/cloudflared/<ID-туннеля>.json
ingress:
  - hostname: data.example.ru
    service: http://127.0.0.1:8780
  - service: http_status:404
```

```
sudo cloudflared service install
```

Cloudflare терминирует TLS: между пользователем и Cloudflare трафик шифруется, а Cloudflare технически видит запросы (адреса публичных страниц и ключ
в заголовке). Внутри VPS трафик идёт по `127.0.0.1`. В приложении укажите `https://data.example.ru` и ключ.

## Обновление

Автоматически: `tinvest-update.timer` в 03:00 МСК запускает `server/deploy/tinvest-update.sh`. Скрипт делает `git fetch` обоих
репозиториев, при новых коммитах в `main` переключает код, проверяет, что Python-файл компилируется, перезапускает сервис и через 5 секунд
проверяет, что он жив (для сервера данных ещё и `/v1/health`). Если сервис не поднялся, код откатывается на прежний коммит.
Без изменений ничего не перезапускается: ежедневный перезапуск «на всякий случай» не нужен, упавший сервис systemd поднимает сам (`Restart=always`).

Вручную, не дожидаясь ночи: `sudo systemctl start tinvest-update && journalctl -u tinvest-update -n 20`.

Если поменялись сами юниты в `server/deploy/`, скопируйте их заново в `/etc/systemd/system/` и выполните `sudo systemctl daemon-reload`.
Кэш в `/var/lib/tinvest-server` сохраняется. Чтобы сбросить его целиком, остановите сервис и удалите `cache.sqlite*`.

## Вход по ключу из Telegram-бота

Доступ к приложению выдаёт бот `@tanalyticbot` (по умолчанию; меняется флагом `--bot`): он присылает ключ вида `TIA-XXXX-XXXX-XXXX`, действующий 7 дней.
Бот живёт в **отдельном закрытом репозитории** и пишет в SQLite-файл, который этот сервер только читает (файл общий, режим WAL):

```
python3 tinvest_server.py --keys-db /var/lib/tinvest-bot/keys.sqlite --bot tanalyticbot
```

Контракт базы (создаёт и ведёт бот):

```
users(tg_id INTEGER PRIMARY KEY, username TEXT, first_name TEXT, created REAL, consent REAL,
      banned INTEGER NOT NULL DEFAULT 0, plan TEXT NOT NULL DEFAULT 'free')
keys(key_hash TEXT PRIMARY KEY, tg_id INTEGER NOT NULL, created REAL NOT NULL, expires REAL NOT NULL,
     revoked INTEGER NOT NULL DEFAULT 0, last_used REAL)
```

`key_hash = sha256(normalize(key))` в hex, `normalize(k) = k.strip().upper().replace(" ", "")`; время — unix-секунды. Сами ключи в базе не хранятся.

Ключ принимается, если запись есть, `revoked = 0`, `expires` в будущем и пользователь не забанен. Клиент получает идентификатор `tg:<tg_id>`.
Отказ приходит как 401 с `error`: `invalid` (неизвестный ключ), `expired` (истёк или отозван), `banned`.

- Проверки кэшируются в памяти: успешные на 60 секунд, но не дольше `expires`; отказы на 10 секунд. Отзыв ключа и бан действуют с задержкой до минуты.
- Сервер сам пишет в базу только `keys.last_used` (не чаще раза в минуту на ключ, ошибки блокировки игнорируются). База открывается отдельным соединением на поток, с `busy_timeout`.
- Если базу не удалось открыть, запросы с ключами получают 401, в журнал один раз пишется причина; сервер не падает.
- Общий `--key` продолжает работать наряду с ключами бота (подходит для своих клиентов и мониторинга). Если не задано ни то ни другое, доступ открыт.
- В приложении по умолчанию используется `https://aurora-bot.duckdns.org:8443/tinvest`; токен Т-Инвестиций на сервер и в бот не передаётся.

## Уведомления через бота

Приложение больше не требует личного бота (токен и chat id): уведомления (тревоги мониторинга, наблюдение и цели, ближайшие выплаты, ежедневная сводка,
тестовое сообщение) отправляет тот же бот, что выдаёт ключ. Telegram ID пользователя известен по ключу.

`POST /v1/notify` с заголовком `X-Client-Key` (только ключ из бота) и телом `{"text": "<b>HTML</b> Telegram"}`:

| Ответ | Когда |
|---|---|
| 200 `{"ok":true,"queued":<id>}` | сообщение поставлено в очередь |
| 400 `{"error":"empty_text"}` / `{"error":"text_too_long","max":3500}` | пустой текст или длиннее 3500 символов |
| 401 | ключ не принят (`invalid`/`expired`/`banned`) |
| 403 `{"error":"уведомления доступны только по ключу из бота"}` | общий `--key` или открытый сервер: адресата нет |
| 402 `{"error":"pro_required"}` | у пользователя нет Pro (`users.plan_until` пуст или в прошлом; в базе без колонки — всегда Free) |
| 409 `{"ok":false,"error":"notify_off"}` | пользователь выключил уведомления в боте (`/notify_off`) |
| 429 `{"ok":false,"error":"rate_limit"}` | больше 30 сообщений в час или 200 в сутки на пользователя |

Сервер вставляет строку в таблицу `outbox` общей базы (создаёт её `IF NOT EXISTS`, если бот ещё не обновлён) и записывает отметку в `notify_log`; лимиты считаются
по ней, поэтому переживают перезапуск. Дальше сообщение забирает бот (поток-отправитель раз в ~2 секунды), отправляет с `parse_mode=HTML`
и удаляет строку. Схема версии 2 (ведёт бот): `outbox(id, tg_id, text, created, tries)`, `notify_log(tg_id, created)`, `users.notify INTEGER NOT NULL DEFAULT 1`.

Конфиденциальность: текст проходит через сервер данных и бот и после доставки нигде не хранится; в журналы (в том числе при `--verbose`) он не попадает.
Сообщения, которые не удалось доставить за час, удаляются. Уведомления приходят, только пока приложение запущено.

## Тарифы Free / Pro

Тариф берётся из `users.plan_until` общей базы (Pro, пока `plan_until > now`; схема v3, ведёт бот; без колонки все пользователи Free). Кэш ключей не переживает конец Pro. Сервер принудительно проверяет Pro только для `/v1/notify` (402). Остальное разграничение (страницы-инструменты анализа, подсказка по оферте, прогноз налога, лесенка) сделано в клиенте как UX: код приложения открыт, поэтому клиентские блокировки обходятся правкой кода, и это допустимо. Данные не защищены тарифом, ограничивается удобство и уведомления через бота. Токен Т-Инвестиций не покидает компьютер на любом тарифе. При обновлении на VPS сначала перезапустите бота (миграция v3), затем сервер.

## Серверные расчёты (индекс страха и жадности): `calc_worker.py`

Тяжёлые расчёты по публичным данным (сейчас — индекс страха и жадности: первый расчёт ≈ 2 000 запросов к ISS, на VPS — десятки минут; скачанные дни сохраняются в `calc_home`, после перезапуска расчёт продолжается, а следующие пересчёты занимают секунды; ход расчёта пишется в журнал раз в минуту) считаются на сервере один раз, клиенты
забирают готовый JSON, а при недоступности сервера считают у себя, как раньше. Токен T-Invest не нужен. Установка:

```sh
sudo cp server/deploy/tinvest-calc.service /etc/systemd/system/ && sudo systemctl daemon-reload
sudo systemctl enable --now tinvest-calc
```

Воркер (`python3 server/calc_worker.py --data DIR [--only fng] [--once]`) импортирует собранный `tinvest_analytics.py` из клона репозитория
(сервер данных у него выключен, кэш в `<data>/calc_home`), раз в ~15 минут пересчитывает расчёты из реестра и атомарно пишет
`<data>/calc/<имя>.json` = `{"t", "data"}`; при ошибке остаётся прежний файл. Чтение: `/v1/parsed/calc/<имя>` (имя `[a-z0-9_]+`); результат
старше часа и неизвестное имя дают 404 (клиент считает сам). Новый расчёт — одна строка в `register_calcs()`. `tinvest-update.sh`
перезапускает `tinvest-calc` вместе с сервером, если юнит включён.

## Потоки денег и стакан («Кто покупает»): `flows_worker.py`, `tinvest_md.py`

Экран «Кто покупает»: куда идут деньги (акции / облигации / фонды / сектора), крупные сделки, всплески объёма и стакан.

**Токен владельца (только чтение).** Нужен для реального времени (сделки и стакан T-Invest). Без токена всё работает по ISS Мосбиржи
с задержкой ~15 минут, стакан в клиенте берётся по токену самого пользователя. Токен **только на VPS, в git его нет**; он должен быть
*только для чтения* (не «полный доступ», не «торговый»). Установка:

```sh
sudo install -d -m 700 /etc/tanalytic
sudo install -m 600 -o root /dev/stdin /etc/tanalytic/tinvest_token     # вставьте токен, Enter, Ctrl+D
sudo cp server/deploy/tinvest-flows.service /etc/systemd/system/ && sudo systemctl daemon-reload
sudo systemctl enable --now tinvest-flows && sudo systemctl restart tinvest-server
```

Порядок поиска токена (`tinvest_md.load_token`): `$CREDENTIALS_DIRECTORY/tinvest_token` -> `$TINVEST_SERVER_TOKEN` -> файл `--token-file`.
В юнитах выбран вариант без `LoadCredential=` (он роняет юнит, если файла нет): перед запуском `ExecStartPre=+…` (от root) копирует
`/etc/tanalytic/tinvest_token`, если он есть, в `/run/tinvest-{server,flows}/tinvest_token` (tmpfs, 600, владелец — пользователь сервиса),
а `--token-file` указывает туда. Нет файла — функции T-Invest выключены, всё остальное работает.

**Защита.** `tinvest_md.py` вызывает только методы из белого списка (MarketData: GetCandles, GetLastTrades, GetOrderBook, GetLastPrices,
GetTradingStatus; Instruments: Shares, Bonds, Etfs, GetAssetFundamentals, GetAssetReports, GetDividends, GetBondCoupons, FindInstrument,
GetInstrumentBy); счета, портфель, операции и заявки недоступны. Токен маскируется (`t.***1234`) в журналах и ошибках и никогда не
попадает в ответы. Тест `tests/test_flows.py` сканирует репозиторий на строки вида токена. Лимиты (токен-бакет): MarketData сборщик
200/мин (`--md-rate`) + сервер 100/мин на живые запросы; Instruments 100/мин (сервер 30/мин); интерактивные запросы имеют приоритет.

**Сборщик** (`python3 server/flows_worker.py --data DIR [--token-file F] [--once] [--stats] [--verbose]`, юнит `tinvest-flows.service`):
универсум — акции TQBR + ~150 облигаций (TQCB/TQOB) + ~40 фондов (TQTF и ETF в TQBR) по обороту дня, обновляется раз в 30 минут.
Сделки: T-Invest `GetLastTrades` по кругу (весь список за ~2–3 минуты) и ISS `trades.json` по курсору `TRADENO` (поле `BUYSELL`).
Хранятся только агрегаты по 5 минутам (45 дней), крупные сделки (30 дней) и всплески. Крупная сделка = не меньше max(5 млн ₽ акции/фонды,
10 млн ₽ облигации; 99-й перцентиль сумм сделок бумаги за 20 дней). Всплеск = оборот 10 минут >= 3× медианы того же слота за 20 торговых
дней (10-минутные свечи ISS) и >= 1 млн ₽. База `flows.sqlite`.

**Чтение (через `/v1/parsed/`):** `flows/summary?period=5m|1h|day`, `flows/instrument?secid=&period=`, `flows/large?since=&class=share|bond|fund&min=&secids=&isins=`,
`flows/spikes?since=`, `flows/instruments`, `flows/status` — из базы, без кэша; живые `md/orderbook?secid=&depth=20` и `md/trades?secid=&minutes=60`
(кэш 1,5 с на бумагу, single-flight; без токена — 404 `no_token`).
Дивиденды и фундаментал акций TQBR для клиентов без своего токена: `md/dividends?secid=` (кэш 12 ч), `md/fundamentals` (все акции, пачки по 100,
кэш 6 ч, фоновый приоритет), `md/reports?secid=` (следующая отчётность, кэш 24 ч); список акций (тикер → uid/assetUid) кэшируется на сутки.
